# Lab 1: Vector Operations and Activations — Векторные операции и активации

## Описание

Реализованы собственные CUDA-ядра для трёх поэлементных операций над векторами `float`:

- сложение векторов: `out[i] = a[i] + b[i]`;
- SAXPY: `out[i] = alpha * a[i] + b[i]`;
- ReLU: `out[i] = max(0, a[i])`.

Каждая операция имеет два варианта обращения к global memory:

- `coalesced` — поток `(blockIdx.x, threadIdx.x)` обрабатывает элемент
  `i = blockIdx.x * blockDim.x + threadIdx.x`; соседние потоки одного warp
  читают и пишут соседние элементы;
- `noncoalesced` — поток `(blockIdx.x, threadIdx.x)` обрабатывает элемент
  `j = threadIdx.x * gridDim.x + blockIdx.x`; потоки одного warp обращаются
  к элементам с шагом `gridDim.x`. Логическая операция и число обработанных
  элементов те же, результат идентичен коалесцированному варианту.

SAXPY пишет результат в отдельный буфер (не in-place), чтобы повторные прогоны
и эталон каждый раз получали одинаковые исходные `a` и `b`.

Для проверки корректности используется эталон NumPy (`a+b`, `alpha*a+b`,
`np.maximum(a, 0)`) и CPU-сверка внутри самой программы. Ядра написаны руками;
библиотечные операции применены только как эталон.

## Компиляция

Из каталога лабораторной:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target submission
```

При необходимости архитектуру GPU задать явно, например
`-DCMAKE_CUDA_ARCHITECTURES=90` (или 120 для RTX 5070). Дополнительных
библиотек, кроме CUDA runtime, не требуется.

## Запуск

```bash
./build/submission --help
./build/submission --input data/example.txt --output results/add.out
./build/submission --input data/rand_257.txt --output results/noncoalesced.out --mode noncoalesced
./build/submission --input data/rand_10485760.txt --output results/perf.out --mode noncoalesced --block 512 --repeat 20
```

Формат входа `--input` (текстовый): первой строкой число `n`, далее `n` строк
`a b` (float, через пробел). Формат выхода `--output` (текстовый): служебные
строки `mode=`, `n=`, `alpha=` и три секции `add`, `saxpy`, `relu` — по одной
строке значений на секцию.

Параметры:

- `--mode coalesced|noncoalesced` — по умолчанию `coalesced`; оба режима
  выполняют add, SAXPY и ReLU;
- `--alpha <f>` — коэффициент SAXPY, по умолчанию 2.0;
- `--block <n>` — размер блока 1..1024, по умолчанию 256;
- `--repeat <n>` — число замеров после прогрева, по умолчанию 10.

Коды возврата: 0 — успех, 1 — ошибка выполнения, 2 — неверные аргументы или
входные данные. Логи идут в stdout, ошибки — в stderr. Пустой вход (`n=0`)
обрабатывается без запуска ядер: программа пишет пустые секции и завершается
успешно.

## Реализация

Ядра — `src/kernels.cu`, CLI, память и замеры — `src/main.cu`.

Распределение элементов между потоками (паттерн Map). Коалесцированный
вариант: поток `i = blockIdx.x * blockDim.x + threadIdx.x`, поток с `i >= n`
ничего не делает (проверка границы). Размер сетки `grid = (n + block - 1) /
block`, поэтому размеры, не кратные блоку (255, 256, 257), обрабатываются
корректно: «лишние» потоки просто не выполняют работу.

Некоалесцированный вариант использует транспонированную индексацию
`j = threadIdx.x * gridDim.x + blockIdx.x`. Схема биективна на `0..n-1`:
разные потоки не обрабатывают один элемент дважды, все индексы покрываются
ровно по одному разу; лишний диапазон отбрасывается той же проверкой `j < n`.
Потоки одного warp (соседние `threadIdx.x`) обращаются к элементам, удалённым
друг от друга на `gridDim.x`, что даёт некоалесцированные обращения к global
memory при том же объёме работы.

Выделение памяти: три буфера по `4n` байт (`a`, `b` и общий выходной `out`,
так как add, SAXPY и ReLU идут последовательно и пишут в один буфер)
на GPU через `cudaMalloc`; передача — `cudaMemcpyAsync` в одном stream.
Все CUDA-вызовы обёрнуты в `CUDA_CHECK`, после запуска ядер проверяется
`cudaGetLastError`; память освобождается (`cudaFree`) перед завершением.
Время измеряется CUDA events в том же stream с явной синхронизацией
(`cudaEventSynchronize`), поэтому учитывается асинхронность GPU.

## Проверка корректности

Эталон — NumPy (`numpy`): `a + b`, `alpha * a + b`, `np.maximum(a, 0)`.
Проверка — `tests/verify.py` (допуск `atol=1e-5 + rtol·( |a|+|b| )`, для
SAXPY `|α·a|+|b|`, для ReLU `|a|` — масштаб операндов, а не результата)
и встроенная CPU-сверка `submission` на тех же входах. Для SAXPY ядро и эталон
получают одинаковые исходные `a` и `b`: операция выполняется над прочитанным
входом, входы не модифицируются in-place.

Входы генерирует `tests/gen_data.py` (seed 42, значения `U(-1000, 1000)`,
знаки независимы; отдельный набор — нули). Проверки выполняются скриптом
`tests/run_checks.sh`.

| Операция | Эталон            | Размер               | Особенности входа             | Максимальная ошибка | Результат |
| -------- | ----------------- | -------------------- | ----------------------------- | ------------------- | --------- |
| add      | `a + b` (NumPy)   | 1, 2, 15, 255, 256, 257, 1000, 2^20, 10^7 | знаковые, нули | 6.1e-05 | OK (оба режима) |
| saxpy    | `alpha*a + b`     | те же                | тот же исходный y в ядре и эталоне | 1.22e-04 | OK (оба режима) |
| relu     | `np.maximum(a,0)` | те же                | нули, положительные и отрицательные значения | 0 (точно) | OK (оба режима) |

Все прогоны `tests/run_checks.sh` (18 размеров × 2 режима) совпали с эталоном
в пределах допуска; на 10^7 максимальное расхождение ядра с эталоном NumPy —
1.271e-04.

Размеры меньше блока и не кратные ему (1, 2, 15, 255, 257), ровно равные блоку
(256) проверены скриптом. Пустой вход: ядра не запускаются, пишется сообщение
и пустой результат (код 0). Неверные аргументы (`--mode bogus`, отсутствие
`--input`, нечисловые значения) и некорректный вход (нечитаемый файл, меньше
2n чисел, отрицательный n) завершают программу с кодом 2 и понятным сообщением
в stderr.

## Результаты

Конфигурация: прогрев — 1 полный цикл перед замерами; `--repeat 20`;
таймеры — CUDA events в вычислительном stream, синхронизация на каждом
прогоне; статистика — медиана; GPU — локально, NVIDIA GeForce RTX 5070
(замеры на кластере Громозека — отдельно).
Время ядра add — от события H2D до события после add; интервалы saxpy и relu
включают D2H-копирование результата после каждого ядра (скалярная сверка CPU
забирает весь выход); D2H — коп relu; полный цикл — от начала H2D до конца
D2H. Выделение памяти в полный цикл не входит: `cudaMalloc` трёх буферов —
порядка 10 мс на 10^7 (замерено отдельно).

| Вариант                  | Размер    | H2D, мс | Ядро add | saxpy+коп | relu+коп | D2H, мс | Полный цикл, мс |
| ------------------------ | --------- | ------- | -------- | --------- | -------- | ------- | --------------- |
| coalesced, block 256     | 1048576   | 0.308   | 0.0136   | 0.219     | 0.213    | 0.203   | 0.957           |
| noncoalesced, block 256  | 1048576   | 0.309   | 0.0610   | 0.269     | 0.246    | 0.215   | 1.117           |
| coalesced, block 128     | 10485760  | 3.476   | 0.2049   | 2.028     | 1.973    | 1.845   | 9.547           |
| noncoalesced, block 128  | 10485760  | 3.449   | 0.5669   | 2.431     | 2.256    | 1.854   | 10.579          |
| coalesced, block 256     | 10485760  | 3.467   | 0.1582   | 2.056     | 1.990    | 1.871   | 9.626           |
| noncoalesced, block 256  | 10485760  | 3.512   | 0.5995   | 2.447     | 2.291    | 1.909   | 10.754          |
| coalesced, block 512     | 10485760  | 3.397   | 0.1644   | 2.040     | 1.988    | 1.865   | 9.489           |
| noncoalesced, block 512  | 10485760  | 3.408   | 0.5745   | 2.433     | 2.247    | 1.864   | 10.576          |

Разница add, saxpy и relu по времени не ожидается — операции почти одинаковы
(чистое ядро relu ≈ чистому ядру add, вычитаемое из интервалов с копом);
сравнение режимов доступа проводится на одном объёме работы.

## Выводы

- В `coalesced` потоки одного warp читают и пишут смежные 4-байтовые слова —
  32 потока укладываются в единицу транзакций памяти; в `noncoalesced` те же
  обращения растекаются по всему диапазону (шаг `gridDim.x`), и каждая транзакция
  несёт полезна только одно слово. Чистое ядро add: 0.0136 мс против 0.0610 мс
  при n=10^6 (в 4.5 раза быстрее), 0.158 против 0.600 мс при n=10^7 (в 3.8 раза)
  — идеальных 8× нет, часть рассеянных обращений покрывают L2 и предвыборка.
- Коалесцированное ядро при n=10^7 даёт ≈760 ГБ/с (120 МБ за 0.158 мс) — это
  уже пропускная способность памяти карты; передача H2D (40 МБ за 3.47 мс ≈
  11.5 ГБ/с) на порядок медленнее ядер и доминирует в полном цикле.
- На малых массивах (n=1000: ядро 0.0027 мс, полный цикл 0.0277 мс) доминирует
  фиксированная стоимость запуска ядер и передач, разница режимов сглаживается,
  и передачи CPU↔GPU стоят дороже самого ядра.
- Размер блока (128/256/512) меняет время ядра на единицы процентов
  (0.158–0.205 мс коалесцированно при n=10^7): сетка и так покрывает все SM,
  запасы потоков достаточны для latency hiding; эффект режима доступа (×3.8–4.5)
  на порядок сильнее эффекта блока.

## Воспроизводимость

### Данные

Входы генерируются скриптом, seed фиксирован (42):

```bash
python3 tests/gen_data.py --n 27 --seed 42 --kind mixed-sign --out data/example.txt
python3 tests/gen_data.py --n 255 --seed 42 --kind mixed-sign --out data/rand_255.txt
python3 tests/gen_data.py --n 256 --seed 7 --kind zeros --out data/zeros_256.txt
```

Формат: первая строка `n`, далее `n` строк `a b`. `alpha=2.0`.

### Полный запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target submission
bash tests/run_checks.sh
```

Скрипт генерирует все входы, запускает `submission` в обоих режимах на
размерах 1, 2, 15, 255, 256, 257, 1000, 2^20, 10^7 и сверяет каждый результат
с эталоном NumPy через `tests/verify.py`. Требуется Python 3 с `numpy`.
Время и медианы печатаются в stdout каждой команды.

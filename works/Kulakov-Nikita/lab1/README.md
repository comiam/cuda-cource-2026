# Lab 1: Vector Operations and Activations — Векторные операции и активации

## Описание

Реализованы три операции над массивами `float`:

- сложение: `add[i] = x[i] + y[i]`;
- SAXPY: `saxpy[i] = alpha * x[i] + y[i]`;
- ReLU: `relu[i] = max(0, x[i])`.

Для каждой операции используется отдельное CUDA-ядро. Реализованы два способа вычисления индекса потока:

- `coalesced`: `index = blockIdx.x * blockDim.x + threadIdx.x`;
- `noncoalesced`: `index = threadIdx.x * gridDim.x + blockIdx.x`.

В режиме `coalesced` соседние потоки обращаются к соседним элементам памяти. В режиме `noncoalesced` соседние потоки одного блока обращаются к элементам с шагом `gridDim.x`. Оба режима обрабатывают одни и те же `N` элементов и дают одинаковые результаты.

Количество блоков рассчитывается как `ceil(N / block)`. В каждом ядре проверяется `index < N`. Размер блока задаётся параметром `--block`, по умолчанию 256.

Данные обрабатываются в формате FP32. Для каждого элемента выводятся три числа: `x + y`, `alpha * x + y` и `max(0, x)`. Порядок элементов сохраняется. При `N=0` создаётся пустой выходной файл, ядра не запускаются.

## Запуск

Справка:

```bash
./build/submission --help
```

Запуск на примере из задания:

```bash
./build/submission --input data/example.txt --output result.txt
./build/submission --input data/example.txt --output result-noncoalesced.txt --mode noncoalesced
```

Параметры:

- `--mode coalesced|noncoalesced` — способ доступа к памяти, по умолчанию `coalesced`;
- `--block N` — размер блока от 1 до 1024 потоков, по умолчанию 256;
- `--repeat N` — число измерений, по умолчанию 10;
- `--warmup N` — число прогревочных запусков, по умолчанию 3.

Входной файл содержит `N alpha`, а затем `N` пар значений `x y`. Выходной файл не содержит заголовка, каждая строка содержит `add`, `saxpy` и `relu`.

Ожидаемый результат для `data/example.txt`:

```text
-1 0.5 0
-4 -4.5 1
4.5 2.5 4
```

Результаты записываются в файл, а время выполнения и сообщения об ошибках выводятся в консоль.

## Реализация

На GPU выделяется память для двух входных массивов (`x`, `y`) и трёх выходных (`add`, `saxpy`, `relu`). Входные данные копируются с CPU на GPU, после чего последовательно запускаются три CUDA-ядра. Затем результаты копируются обратно на CPU, а выделенная память освобождается.

Проверяются ошибки выделения памяти, копирования данных, запуска ядер и освобождения памяти. При ошибках аргументов или входного файла программа завершает работу с кодом `2`, при ошибках CUDA или записи результата — с кодом `1`.

Время измеряется следующим образом:

- `H2D` — передача двух входных массивов с CPU на GPU;
- `Kernel` — суммарное время выполнения трёх ядер;
- `D2H` — передача трёх выходных массивов с GPU на CPU;
- `Полный цикл` — время от выделения памяти до её освобождения, включая копирование и вычисления.

Для H2D, Kernel и D2H используются CUDA events. Полный цикл измеряется CPU-таймером. Выводится медиана по повторным измерениям. Перед ними выполняются прогревочные запуски.

## Проверка корректности

Проверка выполняется командой:

```bash
python3 tests/check.py build/submission
```

Скрипт проверяет оба режима доступа к памяти, размеры массивов `0`, `1`, `255`, `256`, `257`, `513` и размеры блока `128`, `256`, `512`. Всего выполняется 36 сочетаний параметров. Результаты сравниваются с вычислениями на CPU в FP32. Для сложения и ReLU требуется точное совпадение, для SAXPY применяется допуск `1e-5` по абсолютной и относительной ошибке из-за возможного использования FMA.

## Результаты

Замеры выполнены на одном входном файле с `N=1 000 000` и `alpha=0.5`. Для каждого режима использовались размеры блока 128, 256 и 512. Перед измерениями выполнялись 5 прогревочных запусков, затем 30 измерений (`--warmup 5 --repeat 30`). В таблице указаны медианы времени.

| Режим | Block | H2D, ms | Kernel, ms | D2H, ms | Полный цикл, ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| coalesced | 128 | 1.6772 | 0.0643 | 2.7087 | 5.6113 |
| coalesced | 256 | 1.7067 | 0.0667 | 2.7586 | 5.6893 |
| coalesced | 512 | 1.6681 | 0.0661 | 2.6982 | 5.5711 |
| noncoalesced | 128 | 1.6947 | 0.2418 | 2.7433 | 5.8066 |
| noncoalesced | 256 | 1.6792 | 0.2400 | 2.7380 | 5.8071 |
| noncoalesced | 512 | 1.6926 | 0.2432 | 2.7175 | 5.8120 |

В режиме `coalesced` время работы трёх ядер составило 0.0643–0.0667 мс, в режиме `noncoalesced` — 0.2400–0.2432 мс. Таким образом, `coalesced` оказался примерно в 3.6–3.8 раза быстрее именно по времени вычислений на GPU.

Полное время выполнения отличается меньше: около 5.57–5.69 мс для `coalesced` и 5.81 мс для `noncoalesced`. Причина в том, что основную часть полного времени занимают передача данных и другие накладные расходы, а не сами ядра. Сумма медиан отдельных этапов может не совпадать с медианой полного времени, поскольку эти показатели вычисляются отдельно.

## Выводы

В ходе лабораторной работы реализованы и проверены три операции на CUDA: сложение векторов, SAXPY и ReLU. Все 36 автоматических проверок прошли успешно, в том числе для пустого массива и размеров, которые не делятся на размер блока.

На массиве из 1 000 000 элементов режим `coalesced` оказался заметно быстрее по времени выполнения ядер. Лучший результат — **0.0643 мс** при блоке 128 потоков. У `noncoalesced` минимальное время ядер составило **0.2400 мс** при блоке 256 потоков. Это подтверждает, что последовательный доступ соседних потоков к памяти более эффективен, чем доступ с большим шагом.

Изменение размера блока от 128 до 512 не оказало существенного влияния на время вычислений внутри каждого режима. При этом по полному циклу лучший результат показал `coalesced` с блоком 512 — **5.5711 мс**. Поэтому лучший размер блока зависит и от того, какой показатель сравнивается.

Передача данных между CPU и GPU занимает значительно больше времени, чем вычисления. Например, для `coalesced` с блоком 128 сумма H2D и D2H составляет **4.3859 мс**, а выполнение трёх ядер — всего **0.0643 мс**. Поэтому ускорение самих ядер примерно в 3.7 раза приводит лишь к небольшому сокращению полного времени программы.

В результате удалось проверить корректность векторных CUDA-операций и на практике увидеть, как способ обращения к памяти влияет на производительность GPU.

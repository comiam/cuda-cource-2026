# Lab 1: Vector Operations and Activations — Векторные операции и активации

## Описание

Программа выполняет на GPU три операции над векторами типа `float`:

- сложение векторов: `x + y`;
- SAXPY: `alpha * x + y` (результат записывается в отдельный массив, исходный `y` не меняется);
- ReLU: `max(0, x)`.

Каждая операция реализована отдельным CUDA-ядром (`add_kernel`, `saxpy_kernel`, `relu_kernel` в `src/kernels.cu`). Каждый поток обрабатывает один элемент, это паттерн Map.

Есть два режима доступа к памяти, они выполняют одни и те же операции над одним и тем же числом элементов:

- `coalesced` (по умолчанию): соседние потоки warp'а читают и пишут соседние элементы массива;
- `noncoalesced`: соседние потоки warp'а работают с элементами, которые лежат в памяти на расстоянии 32 `float` (128 байт).

Для проверки корректности использованы готовые функции:

- сложение: `thrust::transform` с `thrust::plus`;
- SAXPY: `cublasSaxpy` из cuBLAS;
- ReLU: `thrust::transform` с `thrust::maximum` (максимум из `x` и нуля).

Состав папки:

- `src/main.cu`: разбор аргументов, чтение входного файла, запись результата;
- `src/kernels.cu`, `include/kernels.h`: ядра и функция `compute_on_gpu`, которая копирует данные на GPU, запускает ядра, забирает результат и при необходимости измеряет время;
- `tests/verify.cu`: сравнение с эталоном (thrust и cuBLAS);
- `tests/bench.cu`: замеры времени;
- `tests/run_checks.sh`: проверки командной строки и совпадения режимов;
- `data/example.txt`, `data/example_expected.txt`: пример из задания и ожидаемый результат.

Из каталога лабораторной:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=86
cmake --build build --target submission
```

Программа лежит в `build/submission`. Дополнительные цели `verify` (проверка корректности) и `bench` (замеры) собираются командой `cmake --build build`. Для их сборки нужны cuBLAS и Thrust из состава CUDA Toolkit.

## Запуск

```bash
./build/submission --help
./build/submission --input data/example.txt --output coalesced.txt
./build/submission --input data/example.txt --output noncoalesced.txt --mode noncoalesced
```

Оба режима выполняют add, SAXPY и ReLU.

Аргументы:

- `--input <файл>`: входной текстовый файл;
- `--output <файл>`: файл для результата;
- `--mode <режим>`: `coalesced` (по умолчанию) или `noncoalesced`;
- `--help`: справка, код возврата 0.

Формат входа: в первой строке `N alpha`, затем `N` строк с парами `x y`. Числа разделены пробельными символами, дробная часть пишется через точку, значения читаются как `float`. Коэффициент SAXPY `alpha` берётся из входного файла.

Формат результата: для каждой пары одна строка `x+y alpha*x+y max(0,x)` в исходном порядке, девять значащих цифр, без заголовка. Логи программа печатает в `stdout`, ошибки в `stderr`.

Коды возврата: `0` успех; `1` ошибка выполнения (CUDA) или записи результата; `2` неверные аргументы или входные данные (в том числе нечитаемый файл и число пар меньше `N`).

Поведение при `N = 0`: программа записывает пустой выходной файл, не запускает ядра и завершается с кодом 0.

## Реализация

**Индекс потока и элемент массива.** Размер блока 256 потоков, число блоков округляется вверх: `blocks = (n + 256 - 1) / 256`. Каждый поток вычисляет `i = blockIdx.x * blockDim.x + threadIdx.x`. Например, для `n = 1000` запускается 4 блока, то есть 1024 потока. Поток 231 блока 3 получает `i = 3 * 256 + 231 = 999` (последний элемент), потоки с `i` от 1000 до 1023 ничего не делают благодаря проверке `if (j < n)`. Эта проверка есть во всех ядрах, поэтому размеры, не кратные блоку, обрабатываются корректно.

**Режим coalesced.** Поток с номером `i` обрабатывает элемент `j = i`. 32 потока warp'а обращаются к 32 подряд лежащим `float`, то есть к 128 байтам, и GPU обслуживает такое обращение небольшим числом транзакций.

**Режим noncoalesced.** Потоки делятся на группы по 1024 (32 warp'а по 32 потока). Внутри группы элементы раскладываются «по столбцам»: поток с номером `lane` в warp'е номер `warp` обрабатывает элемент `group * 1024 + lane * 32 + warp`. Соседние потоки одного warp'а (`lane` и `lane + 1`) попадают на элементы, отстоящие друг от друга на 32 `float` (128 байт). Это перестановка внутри каждой группы из 1024 элементов, поэтому каждый элемент по-прежнему достаётся ровно одному потоку, число операций и число запущенных потоков (с точностью до округления вверх до кратного 1024) такие же. Если `n` не кратно 1024, число потоков округляется вверх до кратного 1024, а лишние потоки отсекаются проверкой `j < n`. Правильность отображения проверена отдельно: для 14 размеров (от 1 до 100000) каждый элемент обрабатывается ровно одним потоком.

**Память и копирование.** Функция `compute_on_gpu` выделяет на GPU пять массивов `cudaMalloc` (`x`, `y` и три результата), копирует `x` и `y` на GPU (`cudaMemcpy`, H2D), запускает три ядра, копирует три результата обратно (D2H) и освобождает память `cudaFree`. SAXPY пишет в свой массив, поэтому исходный `y` остаётся нетронутым и используется и для add, и для эталона.

**Ошибки CUDA.** Каждый вызов CUDA API проверяется функцией `check`. После каждого запуска ядра вызывается `cudaGetLastError()` (ошибки запуска), в конце `cudaDeviceSynchronize()` (ошибки выполнения). При ошибке программа печатает сообщение в `stderr` и завершается с кодом 1.

**Измерение времени.** Для H2D, ядер и D2H используются события CUDA в одном потоке (`cudaEventRecord`, `cudaEventElapsedTime`). Полный цикл H2D → ядра → D2H измеряется и событиями, и CPU-таймером (`std::chrono::steady_clock`). Выделение памяти `cudaMalloc` измеряется отдельно (CPU-таймером) и в полный цикл не входит.

## Проверка корректности

**Эталон.** Эталонные результаты считаются на GPU готовыми функциями: add через `thrust::transform` и `thrust::plus`, ReLU через `thrust::transform` и `thrust::maximum` с нулём, SAXPY через `cublasSaxpy`. cuBLAS перезаписывает `y`, поэтому эталону передаётся копия исходного `y`, а наше ядро получает тот же исходный `y`.

**Входные данные** (`tests/verify.cu`): три вида для каждого размера: случайные числа от -10 до 10 (генератор `std::mt19937`, seed `12345 + N`), нули (`+0` и `-0`), чередование знаков с целыми значениями. Коэффициент `alpha = 0.75`.

**Допуски.** Для add и ReLU результат должен совпадать точно (`+0` считается равным `-0`). Для SAXPY допускается разница в округлении (отдельные умножение и сложение или FMA): `|наш - эталон| <= 4 * FLT_EPSILON * (|alpha * x| + |y|)`.

Результат `./build/verify`: для всех 14 размеров и обоих режимов максимальная ошибка add, SAXPY и ReLU равна 0 (результаты совпали с эталоном побитово), итог `ALL OK`.

## Выводы

**Coalescing.** Время ядер при `noncoalesced` больше, чем при `coalesced`, и разница растёт с размером массива: для N = 262144 в 1.6 раза (0.198 против 0.125 мс), для N = 4194304 в 1.6 раза (0.936 против 0.571 мс), для N = 16777216 в 2.0 раза (3.101 против 1.532 мс). При N = 1024 и 16384 ядра работают 0.008–0.012 мс, и разница в 0.002–0.004 мс близка к разрешению измерения; здесь время определяется в основном запуском ядра, а не обращением к памяти. Для блока 256 (таблица 2) эффективная пропускная способность `coalesced` около 364 ГБ/с против около 175 ГБ/с у `noncoalesced`, то есть в 2.1 раза меньше. Причина в организации обращений: в `coalesced` 32 потока warp'а читают 128 подряд идущих байт, и такое обращение обслуживается небольшим числом транзакций памяти. В `noncoalesced` каждый поток warp'а обращается в свою 128-байтную область, и на одно обращение warp'а требуется намного больше транзакций, при этом из каждой загруженной порции памяти потоку нужны всего 4 байта.

**Размер блока.** В режиме `coalesced` блоки от 64 до 1024 потоков дали время ядер 1.41–1.49 мс (разброс около 6 %, лучший результат 128: 1.409 мс), блок 32 заметно хуже (1.926 мс, в 1.4 раза медленнее лучшего). В режиме `noncoalesced` разброс заметнее: от 3.074 мс (блок 256) до 4.353 мс (блок 32), блок 1024 тоже хуже (3.604 мс). Причину этих отличий мы не исследовали. Каждое значение это медиана одной серии, поэтому отличия в единицы процентов нельзя считать значимыми. Универсального оптимума нет: для этой видеокарты разумно брать 128–256.

**Передачи CPU↔GPU и вычисление.** В нашей задаче передачи данных многократно дороже вычисления. При N = 16777216 копирование на GPU заняло 23.8 мс, обратно 35.8 мс, а три ядра 1.5 мс, то есть ядра составляют около 2.6 % полного цикла (при `noncoalesced` около 5.3 %: ядра в 2 раза медленнее, но на полном цикле почти не видны, 59.7 против 58.9 мс в пределах разброса). Скорость копирования получается около 5.6 ГБ/с в обе стороны (H2D: 2 массива по 64 МиБ за 23.8 мс; D2H: 3 массива за 35.8 мс; D2H дольше только потому, что копируются три массива вместо двух), а ядра работают с памятью GPU на скорости около 360 ГБ/с, то есть примерно в 65 раз быстрее. Операции в этой работе очень лёгкие: на каждый элемент приходится одно сложение, одно умножение со сложением и одно сравнение, а переносится 20 байт (2 числа туда, 3 обратно). Поэтому вынос на GPU такой операции окупается, только если данные остаются на GPU и над ними выполняется много операций подряд. Для малых массивов картина та же: при N = 1024 ядра занимают 0.008 мс из 0.296 мс полного цикла (около 3 %), основное время уходит на фиксированные накладные расходы запуска копирований. Выделение памяти `cudaMalloc` (0.27–0.35 мс при N = 1024, 2.3–3.2 мс при N = 16777216) тоже сравнимо или больше времени самого вычисления, поэтому в реальных программах память выделяют один раз и переиспользуют. Для одинаковых по смыслу измерений `alloc` значения заметно различаются между строками (например, 3.233 и 2.339 мс при N = 16777216), то есть измерение выделения памяти шумное.

**CPU-таймер и GPU-таймер.** Полный цикл по CPU-таймеру немного больше, чем по событиям GPU: на 0.1 мс при N = 1024 и на 5 мс при N = 16777216. Вероятная причина: CPU-таймер включает работу CPU при копировании из обычной (pageable) памяти и ожидание синхронизации, которые не полностью видны на временной шкале GPU. Мы это отдельно не проверяли. Закреплённая (pinned) память в этой работе не использовалась, возможно, с ней копирование было бы быстрее.

**Ограничения.**

- Индексы и размеры в коде типа `int`, поэтому поддерживаются массивы до порядка двух миллиардов элементов (на практике раньше упираемся в память GPU).
- Вход читается функцией `fscanf`, значение `N` должно быть целым числом в десятичной записи; числа вида `3.0` в качестве `N` не поддерживаются.
- При ошибке CUDA программа завершается с кодом 1 без явных вызовов `cudaFree`; память GPU освобождается при завершении процесса.
- Размер блока в `submission` фиксирован (256); другие размеры доступны только в `bench`. Они должны быть степенью двойки от 32 до 1024.
- Замеры сделаны на видеокарте ноутбука в WSL2 за один запуск `bench`; на другом оборудовании цифры будут другими.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=86
cmake --build build
./build/submission --input data/example.txt --output coalesced.txt
./build/submission --input data/example.txt --output noncoalesced.txt --mode noncoalesced
diff data/example_expected.txt coalesced.txt
diff data/example_expected.txt noncoalesced.txt
bash tests/run_checks.sh
./build/verify
./build/bench
```
